01 / Executive Summary

Purpose & design decision

Augment the existing Salesforce QuickBooks integration with AI-powered diagnostics, mapping suggestions, duplicate analysis, and a contextual assistant, while keeping core synchronization deterministic and independent.

Optional intelligence

RAIN failures must not block existing QuickBooks synchronization.

No package dependency

All external communication happens over a verified RAIN REST contract.

Secure by design

API keys stay server-side; external payloads are minimized and authorized.

Evidence boundary: This document is based on the agreed requirements, not inspection of the local source repositories. The RAIN API authentication header, endpoints, packaging model, credential-store suitability, and existing class names require code verification before implementation.

02 / Scope

Scope, non-goals & source locations

Included

  • RAIN key configuration and connection testing
  • Sync error analysis and remediation suggestions
  • Dynamic field-mapping recommendations
  • Advisory duplicate analysis
  • Contextual read-only assistant
  • Automated tests, security and upgrade assessment

Not included in first release

  • Automatic AI-generated record writes or merges
  • Unapproved production deployment
  • Changes to RAIN API server contracts unless required and authorized
  • Replacing existing QuickBooks auth or sync logic
  • Unverified RAIN tools, models, or endpoints

First discovery task: inventory QuickBooks synchronization entry points, company records, mapping persistence, Apex tests, RAIN API routes/middleware, and relevant package metadata. Any API method or class name listed below is a proposed interface until validated against repository code.

05 / Authentication & Secrets

API key lifecycle without Named Credentials

Use the RAIN-issued API key for outgoing requests. Its header name must be taken from the RAIN authentication middleware: it could be x-api-key, Authorization, or another specified header.

Security gate: Remote Site Settings are endpoint allowlists, not a secure credential vault. Do not ship the integration with plaintext API keys in Apex, unprotected metadata, browser storage, Custom Labels, or logs. If a suitable secret store cannot be proven for the actual packaging model, block authenticated deployment until resolved.

Proposed lifecycle

  1. Provision: A privileged administrator enters an API key once into a masked field in QBSetup.
  2. Persist: Apex validates permission and writes to a proven package-protected server-only store; never echoes the value.
  3. Test: The server calls a verified harmless RAIN endpoint and reports only connection status.
  4. Use: API client reads the key and sets the verified request header during an allowed HTTPS callout.
  5. Rotate: Replace the key atomically with an approved key and track metadata, not the secret.
  6. Remove: Clear local key/disable integration; revoke at RAIN only if an authorized revocation API is confirmed.

Credential storage decision matrix

Option Assessment Decision
Protected Custom Setting Candidate for managed-package Apex-only access; test 1GP/2GP behavior, subscriber provisioning, exposure surfaces and size limits Validate first
Protected Custom Metadata Protection and runtime mutation / subscriber administration characteristics differ; avoid assuming fit Evaluate
Custom Apex Crypto design Requires independent secure encryption-key custody; encryption with adjacent recoverable key is weak Only if justified
Named / External Credentials Explicitly excluded by project requirements Do not use
Plaintext label / unprotected record / localStorage Inadequate protection for long-lived API secret Prohibited

Admin UI data contract

getRainStatus() should return only enabled, configured, lastValidatedAt, sanitizedStatus, and feature toggles. The one-time saveRainApiKey(key) operation must require explicit administrative authorization and must never echo the submitted key.

07 / Feature Specifications

Five delivery capabilities

F1. RAIN setup & connection test Foundation

Extend QBSetup with Enable RAIN, one-time masked API key entry, Test Connection, Replace Key, Remove Key, status, and feature toggles. A non-admin must not be able to manage credentials. Enabling RAIN without a verified key must be rejected or presented as not configured.

F2. AI sync diagnostics P1

Add Analyze with RAIN on eligible QBSync log rows. Send error category, entity type, sync phase, and minimum authorized mapping context. Render summary, probable cause, remediation and uncertainty; use the existing log UI for navigation. Advisory only.

F3. Mapping suggestions P1

From the current dynamic source entity and target Salesforce object, send accessible schema metadata. Show suggested source/target fields with explanation and confidence when returned. Validate target type, writability, required fields and mapping conflicts server-side. User explicitly accepts before persistence.

F4. Advisory duplicate analysis P2

First run deterministic realm + QuickBooks entity identity matching, then configured duplicate rules. Only unresolved ambiguity enters AI analysis. AI output never creates an identity link, overwrites existing values, or merges records without a separate validated user action.

F5. Contextual assistant P2

Embed a compact qbRainAssistant LWC with company context, chat, suggestions, errors, reset, and keyboard support. Provide read-only, server-authorized tool results such as sync summary, failed logs, mapping state, and connection status. RAIN remote tool calling is optional until contract verification.

Execution rule: AI features should run as user-invoked or appropriately asynchronous auxiliary operations, never as a mandatory step before a core QuickBooks sync can succeed.
08 / Data Isolation

Company and tenant boundaries

RAIN API key scope and QuickBooks connected-company scope are separate concerns. Determine if the RAIN key is per Salesforce installation, per tenant, or per QuickBooks connected company from actual RAIN server authorization logic.

Selected Company AExplicit company context
→
Apex authorizationUser access + realm binding + log ownership
→
Company A payloadMinimum metadata / diagnostics only
  • Always resolve server-side company records; an LWC-supplied realmId is not sufficient authorization.
  • Prevent silent fallback to default/current company in Batch/Queueable flows.
  • On company switch, invalidate and reload assistant context; do not reuse another company's result cache.
  • Data access honors appropriate sharing and CRUD/FLS; privileged integration access must be explicitly justified and bounded.
  • Store correlation IDs, rather than sensitive source data, in new diagnostics where feasible.
  • Never assume an instance-wide RAIN API key grants unrestricted QuickBooks company access.
09 / Reliability

Failure handling and operational behavior

Condition Handling Core QuickBooks sync
RAIN disabled / missing key Hide actions or show setup-required state Unaffected
401/403 Show sanitized authentication/authorization failure, never expose key Unaffected
429 Bounded backoff respecting API guidance; no unbounded queue chains Unaffected
5xx / transient timeout Controlled retry only for idempotent read/analysis requests Unaffected
Malformed AI response Reject schema, show safe fallback, record correlation ID Unaffected
Company disconnected Reject company-context access and new AI actions Disconnection policy applies
External service data leak concern Disable feature, scrub logs, initiate incident process Unaffected unless incident policy requires otherwise

Instrument status codes, latency, error category, feature, correlation ID, and selected internal company reference. Avoid storing entire prompts, responses, or personally identifiable record values by default; apply explicit retention policy.

12 / Deployment

Installation, enablement & rollback

Pre-deployment checks

  • Confirm whether package is 1GP or 2GP and its namespace constraints.
  • Approve credential storage model and verify subscriber configuration.
  • Verify RAIN API header, approved paths, rate limits and key scope.
  • Review Remote Site Setting packaging and post-install state.
  • Define custom permission and admin access policy.
  • Complete required privacy disclosures and integration opt-in.

Deployment sequence

  1. Deploy optional metadata and permissions; keep RAIN disabled.
  2. Deploy Apex client/services, DTOs, unit tests, and new LWC code.
  3. Install or upgrade in a sandbox/scratch org representative of a subscriber.
  4. Configure/activate Remote Site Setting as required by the package model.
  5. Admin registers an API key and tests connectivity.
  6. Enable diagnostics, then mapping; later enable duplicate analysis and assistant.
  7. Run QuickBooks sync regression and monitor sanitized RAIN telemetry.

Rollback

Disable RAIN feature flags and remove local API key configuration. Existing QuickBooks sync paths must remain independent. Revert new UI exposure if necessary, but avoid deleting durable metadata or existing package records. If a secret may have been compromised, rotate/revoke it at RAIN; local removal is not equivalent to remote revocation.

15 / Definition of Done

Acceptance criteria

  • QuickBooks package installs and operates without the RAIN managed package.
  • RAIN authentication uses an actual validated API key contract.
  • No Named Credentials or External Credentials are introduced.
  • Secrets remain server-side under validated protected storage.
  • All RAIN callouts use HTTPS and allowlisted Remote Site Settings.
  • RAIN setup supports masked key registration, replacement, connection test, and removal.
  • Diagnostics works for authorized sync logs without changing records.
  • Mapping suggestions work with dynamically selected Salesforce objects.
  • Duplicate AI remains advisory and deterministic matching remains authoritative.
  • Assistant is company-aware and limited to authorized read-only tools.
  • Multi-company data isolation is verified with tests.
  • Core sync works unchanged when RAIN is disabled, invalid, or unavailable.
  • CRUD/FLS, sharing, injection, XSS, and privacy controls are tested.
  • Actual static analysis reports and honest test evidence are retained.
  • Deployment, subscriber setup and rollback procedures are documented.
Target outcome: An optional, secure AI layer that improves QuickBooks administration and synchronization diagnostics without weakening company isolation, security-review posture, or core integration availability.
